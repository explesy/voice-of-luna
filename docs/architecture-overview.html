Voice of Luna architecture

The short version

Voice of Luna is a local voice shell over Codex. The browser handles the human interaction. The FastAPI backend coordinates the turn. Speech adapters handle STT and TTS. Codex produces the model answer. Plugins add specialized workflows without bloating the neutral core.

Main layers

1

Human conversation

Microphone, VAD, radar HUD, text dock, playback, and barge-in.

2

Local orchestration

FastAPI, conversations, WebSocket events, cancellation, and local state.

3

Model runtime

Local Codex app-server, model discovery, streamed text turns, and reasoning settings.

4

Workflow plugins

Project Room, Voice Trainer, and the planned development-control plugin.

Runtime flow

Browser
Captures speech, detects endpoint, displays status, plays audio, interrupts on barge-in.
Backend
Receives the turn, orders events, manages transcript and cancellation.
STT / Codex
Local speech recognition turns audio into text; Codex streams the assistant answer.
Speech pipeline
Chunks early clauses and sends them to TTS before the full answer is complete.
Playback
The browser receives audio chunks and starts speaking quickly, while later chunks continue.

Plugin rule

The neutral core should not learn domain concepts. Relationship training, project context, GitHub state, coaching flows, and development supervision belong in plugins.

  • Project Room owns project context and evidence.
  • Voice Trainer remains a separate plugin/product.
  • Development-control plugin should supervise agents, PRs, CI, and review loops.

Infrastructure direction

The next goal is to make the repository easy to drive from a phone through agents and GitHub.

  • Canonical make verify.
  • Fake STT, fake Codex, fake TTS for deterministic CI.
  • Simulated end-to-end browser/backend flow.
  • Mobile-readable PR artifacts: screenshots, traces, logs.

Ownership map

Browser

Owns user interaction, not product memory or model credentials.

Backend core

Owns neutral conversation mechanics, not specialized workflow semantics.

Adapters

Own STT, TTS, and model-provider details behind small interfaces.

Plugins

Own project-specific, training-specific, or development-control behavior.

CI / agents

Should prove routine changes through tests and artifacts so phone-first review is practical.

The practical design question

When the project feels confusing, ask: which layer should own this concept? If it is a specialized workflow, it probably belongs in a plugin. If it is turn-taking, transport, speech, cancellation, or local state, it probably belongs in the neutral core.
